# Firefox page-translation capability probe

Run with `pnpm exec node scripts/dev/page-translation/e2e-firefox/run.mjs`; focused tests use `pnpm test:run scripts/dev/page-translation/page-translation-e2e-firefox.test.js`. The probe re-execs itself in a rootless network namespace and verifies exactly loopback-only addressing with no IPv4 or IPv6 routes before running Firefox or reading browser version. It uses Firefox's announced WebDriver BiDi websocket directly; no geckodriver or automation framework is involved.

The probe subscribes to BiDi request events before registering interception. It continues only loopback fixture traffic and the exact runtime-collector `POST`, provides the known empty startup voice list, fails every other intercepted HTTP(S) request, then closes request admission and drains handlers before teardown. A fresh authenticated runtime bridge binds an inert page in the driver-created tab before extension installation, verifies the instrumented background startup, then navigates that same tab to the fixture and verifies the real content startup/readiness reports and acknowledgment. The bridge proof is separate from BiDi realm inspection: it does not promote `backgroundInspection` or `contentInspection`, and does not bypass gates for native background/content negative-fetch probes. No Firefox extension system-access override is enabled; installation metadata is not treated as execution readiness.

Opt-in prototype: `FIREFOX_E2E_LOOPBACK_TLS_PROXY=1 pnpm exec node scripts/dev/page-translation/e2e-firefox/run.mjs`. It retains the same isolated launcher and refuses to launch before loopback-only/no-route verification. It creates a short-lived CA and `edge.microsoft.com` SAN leaf under the probe temp root, verifies the chain/hostname with OpenSSL, and imports the CA only into the new Firefox profile NSS database (`C,,`). That profile alone receives manual HTTPS proxy prefs pointing to `127.0.0.1`, a localhost bypass, and `network.proxy.allow_hijacking_localhost=false`; no insecure-cert capability or system trust is used. Both CONNECT and TLS terminate on loopback, CONNECT permits only `edge.microsoft.com:443`, and the proxy never opens an upstream connection. This mode invokes the real Edge provider chunk directly through the instrumented provider class and request engine; it does not send `page-translate`, run the Page Scheduler, or inspect/mutate/restore the fixture DOM. Proxy TLS stages are recorded separately from BiDi. DOM acceptance and Restore are explicitly `NOT_TESTED`; this provider-only proof is not full Firefox page-translation E2E and the overall capability summary may remain unsupported.

Phase 1 opt-in full page flow: `FIREFOX_E2E_LOOPBACK_TLS_PROXY=1 FIREFOX_E2E_PAGE_TRANSLATION=1 pnpm exec node scripts/dev/page-translation/e2e-firefox/run.mjs`. This keeps the isolated TLS proxy and authenticated bridge, but sets `providerOnly:false` so the content bridge sends the real production Start command. It uses the test-only Sliced build and a separate deterministic fixture with six text-node targets and six title-attribute targets. A test-build-only hook captures each actual Scheduler `PAGE_TRANSLATE_BATCH` message ID, session ID, and target membership; exact safe evidence is sent over the authenticated content-to-background operation lane and must correlate one-to-one with Background Edge invocations. The harness matches each exact body hash/size/source-index set to a separately held loopback TLS request, then returns only synthetic `mapEdgeResponse` translations. It requires two non-overlapping Scheduler/provider/proxy batches, exact-once coverage of all 12 targets, Bridge DOM acceptance/quiescence and successful real `page-restore`, including exact original text/markup/attribute and metadata restoration. The Phase-1 exit summary requires the startup, sliced flags, proxy/request, provider/Scheduler, acceptance, Restore, and cleanup gates; broad Phase-2 NOT_TESTED fields remain visible but do not gate this scenario. The Provider-only invocation remains unchanged when only the first flag is set. Stop, cancellation, and replacement scenarios are **NOT TESTED** in Phase 1.

Phase 2A Stop Auto proof: `FIREFOX_E2E_LOOPBACK_TLS_PROXY=1 FIREFOX_E2E_PAGE_TRANSLATION_STOP=1 pnpm exec node scripts/dev/page-translation/e2e-firefox/run.mjs`. This is mutually exclusive with `FIREFOX_E2E_PAGE_TRANSLATION=1`. It reuses the same isolated launcher, trusted profile-scoped TLS proxy, six-text/six-title fixture, and test Sliced build. The actual `PAGE_TRANSLATE` start uses auto mode. After the first real Scheduler batch is accepted and the next real Edge request is held, a separate authenticated, bounded control poll routes the real `PAGE_TRANSLATE_STOP_AUTO` command through the extension background to the content handler; provider telemetry remains unblocked while the driver waits for that request. No manager internals, forced socket abort, or fabricated success is used. Success requires exact Scheduler/session/message/physical request correlation; the held socket must close from the production cancellation, the physical attempt and Provider root must settle after the matched controller abort, both production cancellation messages must be acknowledged, active Background resources must drain, accepted DOM must remain translated, and pending targets must remain unchanged with no post-stop target mutations. Native settlement error codes such as `FETCH_ERROR` or `NETWORK_ERROR` remain distinct from the separately proven controller/socket abort. The final authenticated snapshot explicitly rejects acknowledgement-only or false-success evidence. This bounded scenario does not implement Replacement or Stale-Success; those remain **NOT_TESTED**.

Phase 2B Replacement A→B proof: `FIREFOX_E2E_LOOPBACK_TLS_PROXY=1 FIREFOX_E2E_PAGE_TRANSLATION_REPLACEMENT=1 pnpm exec node scripts/dev/page-translation/e2e-firefox/run.mjs`. This is mutually exclusive with `FIREFOX_E2E_PAGE_TRANSLATION=1` and `FIREFOX_E2E_PAGE_TRANSLATION_STOP=1`. It reuses the same isolated launcher, trusted profile-scoped TLS proxy, and test Sliced build, but replaces the Phase-1/2A runtime bridge with a mode-specific authenticated replacement collector and a route-aware fixture whose exact routes are `/` (session A) and `/replacement` (session B). The background seeds only the real auto-rule and DOM-change settings; the content entry only observes. Production starts session A on its own, accepts A's first real batch into the DOM, and its next genuine Edge request is held in the proxy. The driver then clicks the fixture's own control in the page realm, so the trusted same-document `history.pushState` reaches Firefox's navigation event and the production background forwards the real `SPA_NAVIGATION` cursor; nothing synthesizes that message, starts B, or bypasses the production cancellation and ownership guards. The proxy admits a bounded 24-source oracle (the 12 A sources plus all 12 B sources), so any pending subset production leaves unaccepted may legitimately be re-requested with its new B source, and each admitted request still matches one native provider invocation. Success requires distinct authenticated A and B sessions, exact Scheduler/provider/proxy correlation of the three real requests (A released, A held and aborted, B released), a matched controller abort plus separate physical and Provider-root settlement of the held A request, retained A translations owned by B, B-only acceptance of the remaining targets, no post-invalidation A write, an independently recomputed final-DOM hash comparison, production B Stop with released session observers, and harness cleanup. The Stale-Success delivery-barrier scenario is **NOT TESTED** and no released A success is delivered after replacement.

Phase 2C Stale-Success proof: `FIREFOX_E2E_LOOPBACK_TLS_PROXY=1 FIREFOX_E2E_PAGE_TRANSLATION_STALE_SUCCESS=1 pnpm exec node scripts/dev/page-translation/e2e-firefox/run.mjs`. This is mutually exclusive with `FIREFOX_E2E_PAGE_TRANSLATION=1`, `FIREFOX_E2E_PAGE_TRANSLATION_STOP=1`, and `FIREFOX_E2E_PAGE_TRANSLATION_REPLACEMENT=1`, and requires the loopback TLS proxy. It reuses the Phase 2B lane infrastructure (route-aware A `/` → B `/replacement` fixture, authenticated mode-specific stale collector, BiDi session, 24-source TLS proxy oracle) and builds the replacement extension with the opt-in `staleSuccess` content config. The scenario is the stale-successful-delivery rejection: session A's first batch is released and accepted as in Phase 2B; the second A batch's real Edge request is also RELEASED — a genuine fulfilled Provider success, never an abort — and the content-side delivery barrier reports `stale-reply-held` with the reply item count and a reply hash, which the driver recomputes independently against the fixture oracle (`fixture translation: ${targetTexts[index]}`, plain or uniformly U+200E-prefixed). The trusted SPA navigation A→B then runs exactly as in Phase 2B (collector `navigate-to-b` control plus the fixture control click); production cancels session A and starts session B, which retains A's accepted targets and accepts the rest. Once B owns the page, the content's bounded release poll asks the background `release-stale` broker, the background asks the collector's `release-stale` control, and the collector grants it only after the hold and `accepted-B` are admitted — the driver never fabricates the release. Success requires: exactly three provider requests, all released (an aborted request or a fourth retry request fails the scenario); the `stale-reply-released` and `stale-batch-rejected` (outcome `cancelled`) collector events for session A and the stale message id; the hold elapsed time within the 6000 ms ownership-check window (the production reply timeout is 8000 ms, so a later release would be a timeout, not the Scheduler rejection); no controller-abort evidence; the stale batch's physical and Provider-root settlement as clean fulfilled successes; B-owned final DOM where accepted targets carry B's translation, never A's stale text, with no post-invalidation A writes; and an independently recomputed final-DOM hash comparison. Artifact records: `pageTranslationStaleSuccess` (scenario, batch ids, stale-reply ids/counts/hashes only — no reply payload, stale hold timing, proxy request summary, final DOM targets, limitations), `staleSuccessProof` capability gates, and `loopbackTlsProxy` with mode `page-translation-stale-success`.

The runtime authentication token is generated independently per run, used only for the loopback fixture and private worker build configuration, and redacted recursively from BiDi events, command journals, errors, and artifacts. Bridge reports are validated for exact sequence, source entry, sender/tab/frame/URL/navigation identity, readiness checks, and sliced-discovery flags. When the background operation gate returns `start`, the driver sends only the fixed operation release; the content helper issues the real production `page-translate` Edge/fr command. The driver correlates bounded native request attempts to the same logical page-translation session, collects and hashes each actual request body, and serves `mapEdgeResponse` only to a matching paused Edge request. Successful capabilities require exact-once coverage of all 12 fixture sources by fulfilled native attempts, parser/command reports, actual 12-target DOM acceptance, and successful restore. Data-collector or interception limitations are reported independently and Edge is never continued to the network. Provider cancellation and stale-delivery lifecycle checks remain `NOT_TESTED`; this is not the full E2E matrix. Background/content negative fetches remain gated on both actual BiDi realms and exact discovery flags, and are not enabled via the runtime bridge.

An atomic JSON artifact is written to `/tmp/opencode/page-translation-firefox-<run-id>.json` by default. Set `FIREFOX_PROBE_ARTIFACT` to choose its path (the parent directory must already exist). If that path already exists, a run-ID-suffixed path is used so prior artifact bytes are preserved. Results use `SUPPORTED`, `UNSUPPORTED`, `FAILED`, and `NOT_TESTED`. Exit status: 0 only when every required capability is `SUPPORTED`; 2 when a capability is unsupported or gated/not tested; 1 for failure, timeout, protocol, cleanup, or artifact errors. Artifacts include a unique run ID, HEAD and source hashes, runtime versions, commands/events/request outcomes, network-scope evidence, and limitations. This is a bounded capability probe, not the full Firefox E2E suite or 1000-target matrix.
